# CLAUDE.md

This file covers the repository as a whole. A plugin under `plugins/` carries its own `CLAUDE.md` next to its `plugin.json`, and that one is the authority on the plugin's internals.

> **How to read a factual claim in here.** A paraphrase in this file gets trusted as ground truth and has already been used to design a test fixture — where it turned out to be wrong. So: anything stated about repo contents or script behaviour was **re-verified against the files on 2026-08-10** and carries a `file:line` where it is specific. Two claims in here **cannot** be checked from this repo and are marked *(external)* where they appear — the description-length cap and its setting name, and the plugin `hooks/` path (no plugin ships one, so it has never been exercised). A third, the no-nested-subagent constraint, was checked on **2026-08-28 and turned out to be false**; see the subagents section. That is the point of the marking, and the reason to spend the ten minutes: it had sat here unverified for months while a whole architecture was described as resting on it. Treat an *(external)* claim as a working assumption, and if you are about to build on one, verify it against Claude Code's own docs first. Anything else you find unmarked and un-cited is stale by default — check it, then add the citation. The marks and dates here come from the issue-to-pr plugins' own repository, folded into this one on 2026-10-13, and the subagents section they mention now lives in `plugins/test-authoring/CLAUDE.md`.

## What this is

`tundra` is a public Claude Code plugin marketplace. `.claude-plugin/marketplace.json` at the root lists what is on offer, and every entry's `source` is a relative path into `plugins/`.

**Nothing specific to one organisation goes into a plugin here** — no tenant, no internal service, no internal process — because the repository is public. A plugin that needs any of that belongs in a marketplace of its own from the start. Moving it later means every user has to uninstall and re-add, because a plugin's identity is `<plugin>@<marketplace>` and nothing migrates across marketplaces.

## Layout

```
.claude-plugin/marketplace.json     the catalogue, and the only thing /plugin marketplace add reads
plugins/<name>/                     a plugin, with everything it needs inside its own folder
tools/pre_publish_check.py          the publish gates
tools/run_tests.py                  every *_tests.py under a tests/ directory
.githooks/pre-push                  runs both before a push
.github/workflows/checks.yml        runs both again after one, on Linux and Windows
README.md                           the English README, translated by README.zh-TW.md and README.zh-CN.md
docs/issue-to-pr/                   the issue-to-pr plugins' README, its translations and dashboard screenshot, and the root READMEs' smaller copy of it
docs/translation-glossary.md        the vocabulary every translation follows
docs/whoami/                        the root READMEs' whoami thumbnails, a light and a dark version shared by all three READMEs
docs/remind-me/                     the root READMEs' remind-me thumbnails, a light and a dark version cut from a fictional report
docs/banner/                        the root README's banner, a light and a dark version shared by all three READMEs
LICENSE                             covers everything under the root
```

Inside a plugin:

```
plugins/<plugin>/
├── .claude-plugin/plugin.json        # plugin metadata: name, description, version, optional dependencies[]
├── skills/<skill>/SKILL.md           # a user-invocable skill (frontmatter + body)
├── skills/<skill>/evals/evals.json   # skill evals (prompt → expected behaviour + assertions)
├── skills/<skill>/README.md          # optional per-skill doc
├── agents/<agent>.md                 # a subagent (flat dir, bare-name files) — test-authoring only
├── resources/                        # templates / static assets bundled with the plugin
└── docs/                             # deeper design docs
```

**Test suites live beside the code they cover and therefore ship with the plugin** — `plugins/issue-to-pr-pipeline/skills/resolve-issue-dashboard/tests/` is 12% of that plugin's bytes, and a consumer installs it. Measured 2026-09-22 and decided to leave: the plugin format has no exclusion mechanism (no `.claudeignore`, and no `files` / `include` / `exclude` field in any `plugin.json` across the official marketplace), Anthropic's own `security-guidance` plugin ships a `tests/` directory at a similar 8%, nothing reads the directory so the token cost is zero, and moving the suites out would break the co-located sibling that `test-authoring` itself resolves conventions from, turn one `../scripts` hop into five, and leave this repo with two different test layouts. Revisit only if an exclusion mechanism appears — that would buy both halves at once.

**A plugin's folder is the unit that gets copied, so everything a plugin needs lives inside it.** A copied plugin cannot reach a `../shared-utils` outside its own directory, and organisation sync packages each plugin folder on its own.

A plugin is registered in exactly one marketplace, and for a plugin here that marketplace is this one. Two listings would give the same plugin two identities, `<plugin>@tundra` and `<plugin>@<theirs>`, with nothing to stop a user installing both.

Sharing the name `tundra` between two catalogues is not a way round that. Claude Code registers one marketplace per name and replaces the first when a second of the same name is added, with no warning, and a plugin installed from the replaced catalogue then fails to load with `Plugin <name> not found in marketplace tundra`.

## Versions live in plugin.json, and only there

Every plugin declares its `version` in its own `.claude-plugin/plugin.json`. A marketplace entry never does.

**Not both**, because the second copy is inert rather than redundant. The documentation is direct about it: *"Avoid setting `version` in both `plugin.json` and the marketplace entry. Claude Code always uses the `plugin.json` value without warning, so a stale manifest version can mask a version you set in `marketplace.json`."*

**Not neither**, because with no version anywhere the resolved version is the source's commit SHA, so a user asking what they are running gets `c447c3207a42`.

The version in `plugin.json` decides whether a user is offered an update, so a push that changes a plugin without changing its version delivers nothing. The version gate under Making changes catches that.

## Installing from here

```
/plugin marketplace add https://github.com/tundra-east/tundra.git
/plugin install <plugin>@tundra
```

GitHub `owner/repo` shorthand is also accepted and clones over SSH by default, so the shorthand and the HTTPS URL are not the same instruction. Write the full HTTPS URL.

## Anatomy of a skill

A skill is `skills/<name>/SKILL.md` with YAML frontmatter (`name`, `description`) followed by a Markdown body of instructions. Invoked as `/<plugin>:<skill>` or auto-triggered.

The `description` field is **load-bearing**: it is how Claude decides when to auto-trigger the skill. It typically packs three things — what the skill does, "Use when…" trigger phrases, and an explicit "Do NOT trigger for…" list that routes look-alike requests to sibling skills. Preserve this structure and do not compress or shorten descriptions casually; terse descriptions break triggering.

**Description length cap**: there are two caps and the binding one is **not** Claude Code's. The Agent Skills specification — the open format these files are written in, which 26+ agents now read — caps `description` at **1,024 characters**, and the reference validator (`skills-ref validate`) fails anything longer. Claude Code separately truncates at **1,536** (`skillListingMaxDescChars` default) *(external — a Claude Code internal, not checkable from this repo)*, silently hiding whatever sits past it, and the trailing "Do NOT trigger for…" list is exactly what gets cut. So measure the whitespace-normalized length against **1,024** and keep a new description **≤ ~1,000** for headroom — measure it with `PYTHONUTF8=1 uvx --from "git+https://github.com/agentskills/agentskills@main#subdirectory=skills-ref" skills-ref read-properties <skill-dir>` (there is no installed `skills-ref` on PATH — the bare command does not run), never a hand-rolled fold and never the validator without that prefix (see "Measuring anything" for why both mislead, in opposite directions). If space is tight, cut how-it-works mechanism detail (the body covers that after invoke) and quotes that duplicate the trigger-phrase list — never the "Do NOT trigger for…" routing. **This entry used to say ≤ ~1,450, a target derived from the Claude Code cap alone, and 7 of the 14 shipped descriptions were over the spec limit because of it** (#24) — the same ship-behaviour-not-observation failure as the commit-format rules in #22. All 14 skill and 8 agent descriptions were measured and brought under 1,024 on 2026-08-31; the longest is now `resolve-pr-comments` at 997 and the shortest `add-unit-test-agent` at 286. Two limits on this: the old entry's own figure did not reproduce — it named `review-issue-fact` at 1,436 as the longest, but measured on 2026-08-31 that description was 1,290 and the longest was `review-plan-risk` at 1,355 — and whether a given harness rejects, truncates, or ignores an over-length description is *(external)*, unverified for every harness including Claude Code; only the validator's behaviour is confirmed.

## Making changes

- **Editing a skill/agent**: edit the `.md`, then in a consumer session run `/reload-plugins` to pick it up. There is nothing to build.
- **Releasing a version bump**: bump the version in the changed plugin's `.claude-plugin/plugin.json` and push — it is the only version, and the install cache is keyed by it. Bump only plugins whose content changed; every plugin's version moves on its own. The push is the release, because every catalogue entry is a path into this repository and nothing else has to move.
- **Loading the plugins from a clone**: `claude --plugin-dir ./plugins/<name>` loads one plugin as `<name>@inline`, and `claude --plugin-dir ./plugins` loads them all. Never `/plugin marketplace add` the clone: it is a marketplace named `tundra`, so adding it silently replaces the `tundra` you installed from, and every plugin installed from that one then fails to load.
- **Before pushing, derive which plugins need a bump from the diff — do not recall it.** The cache is keyed by version, so a changed plugin at an unchanged version reaches nobody, and the push looks successful. A late commit touching a *different* plugin than the earlier ones is how this slips (it has, once). **This is now mechanical: `python tools/pre_publish_check.py` owns it**, along with the JSON, frontmatter, description-length and public-leak checks that used to be prose here. Enable the gate once per clone with `git config core.hooksPath .githooks` — CI runs the same file, but this repo publishes by direct push, so CI reports after the fact and only the hook can stop the push.
  Two things about the gate are worth keeping in your head rather than only in the tool. It compares against the **published** ref, so it must run against a commit and not the working tree — `git diff` cannot see an untracked file, so a plugin whose only change is a *new* file would report unchanged and the gate would pass the exact case it exists to catch (verified 2026-08-13: pre-commit it read `changed=1`, post-commit `changed=2`; the hook and the workflow both run post-commit for this reason). And `tools/tests/pre_publish_check_tests.py` is what keeps it honest — it plants one defect per gate and asserts no *other* gate reports it, which is the property that makes deleting a gate turn the suite red.
- **Adding a skill**: create `plugins/<plugin>/skills/<skill>/SKILL.md` with `name` + `description` frontmatter; add `evals/evals.json` if it warrants evals.
- **Adding a plugin hook**: no plugin ships one today. If you add one it belongs at `plugins/<plugin>/hooks/hooks.json` *(external, and never exercised — no plugin ships a hook, so this path is unconfirmed)* — a **plugin-root** directory, not inside `.claude-plugin/` and not under `resources/` — and `/reload-plugins` picks it up. Getting the location wrong fails silently: the hook simply never loads.
- **Ship the behaviour, not the observation.** These plugins are installed by people whose conventions we cannot see, so where a value can be *derived from the consumer's own repo*, ship the derivation — not the value we happened to observe here. This has already gone wrong four times in one place: `ad-hoc <summary>`, `acme-xxxxx <summary>` with a ≤50 cap, a flat prohibition on the `Co-Authored-By` trailer justified as "forbidden team-wide", and a `master`-before-`main` base default. Every one was a correct observation of *this* user's internal repos, published as a rule for everyone. The tell is a literal token nobody would invent independently (`ad-hoc`), or a justification that names an authority the consumer is not under ("team-wide"). The fixes are all the same shape — read the repo (`git log --format=%s` for subject shape and length, `git log --format=%b` for the trailer, `git symbolic-ref refs/remotes/origin/HEAD` for the default branch), match what you find, and keep the old value only as the named fallback for when there is no history to learn from. Note this is a *scope* bug, not a missing feature: `open-pr` already had a real learning pass (`SKILL.md:61`), but `:63` limited it to "presentation only", which is exactly the tier these values were not in. The same reasoning as the `model:` decision above, and stronger — a commit format is enforced by the consumer's hooks and CI, so getting it wrong fails their build rather than just costing them tokens.
- **Adding a guard to a skill or agent** (a check that detects a bad state): four traps, all hit within one change here, and they compound. **(a)** Do not build a detector for a state nobody has observed — that is the argument that killed the invariant-harness proposal, and it applies to guards too. **(b)** Every guard needs a boundary, and each boundary puts some legitimate run on the wrong side; each false positive earns a carve-out, each carve-out is a new mechanism, and the new mechanism is the next review round's weakest link. Prefer cutting the guard to adding a third carve-out. **(c)** A guard's inputs must be something someone is *obliged* to produce — check the producing side's own contract, not just that the value exists somewhere. **(d)** Never put a guard downstream of the party it distrusts: a check asking "did you do what you claimed" must not take its trigger, its file list, or its baseline from the claimant. The worst defect found in both halves of one change was exactly this — a spawn gate keyed on the untrustworthy party's own report. **(e) Inventory before you add — including your own recent work.** Grep for the thing you are about to guard against and read what already covers it. This is not the same as (a): the state may be worth guarding and already guarded. A plan step here was written to make `review-plan-risk` re-check a claim class that `review-issue-fact`'s verifier already challenges bidirectionally — **and those two lines had been added the same morning, by the same session that then wrote the step.** Judgement was not the failure; knowing what was already in hand was.

  The four traps above plus this one share a root worth stating on its own: **every one of those fixes was validated against the artifact, never against the world.** Prose can be perfectly self-consistent while its premise is false, its substrate contract forbids it, or the problem is already solved elsewhere — and a review reads the artifact, so a review is structurally blind to all three. Two cheap correctives, and they are not interchangeable: a **fixture** tests the world (does the premise hold, does the mechanism fire), an **inventory** tests what already exists. Run both before writing the guard, not after.
- **Validating**: `python tools/pre_publish_check.py` runs the gates — JSON, frontmatter, description length, version bumps, public-repo leaks and README translations — over every plugin and every translated README. `python tools/tests/pre_publish_check_tests.py` tests the gates themselves, and `python tools/run_tests.py` runs every `*_tests.py` under a `tests/` directory — discovered by glob, because the CI workflow used to name its suites one by one and a new one ran nowhere until somebody noticed. The pre-push hook runs the gates and then the suites, so both stop a push rather than reporting after one, and `.github/workflows/checks.yml` runs them again on Linux and Windows. Anything none of them covers is prose on purpose, because it needs judgement.
- **Rules that belong to one plugin** live beside it: the step registry and the dashboard in `plugins/issue-to-pr-pipeline/CLAUDE.md`, and the subagents, the rule-book boundaries and the skill evals in `plugins/test-authoring/CLAUDE.md`.

## Translations

Six READMEs are translated, each with a `README.zh-TW.md` and a `README.zh-CN.md` beside it: the root one, `docs/issue-to-pr/README.md`, `plugins/issue-to-pr-pipeline/skills/resolve-issue/README.md`, `plugins/test-authoring/README.md`, and the whoami and remind-me READMEs. Any edit to an English one makes both of its translations stale. For the issue-to-pr plugins this set was chosen on 2026-10-05 over translating all eleven of their READMEs: readers mostly stop at the root README and the pages it links to, and the other READMEs together change about three times as often as the root and carry eight times its text.

The `translations` gate in `tools/pre_publish_check.py` finds every `README.md` with a translation beside it, so once a README has one language it needs both, and it is checked from then on with no list to keep up. It checks that each translation records the sha256 of the README it was made from, that its fenced code blocks, link targets, heading outline, table rows and language-switcher line match the README's, and that every in-page link lands on an anchor — a translated heading gets a different GitHub anchor, so a section that English links point at carries an explicit `<a id="…"></a>`. A link into another translated README goes to the same-language version, and the gate fails a link into the English one while a translation exists. The gate prints the current digest when a translation is stale.

Code blocks stay English in every language, because CJK full-width characters break a hand-aligned text diagram such as the pipeline's. A Mermaid diagram is the exception: nothing in it is aligned by hand, so its labels are translated in place, and the gate compares only where the diagram sits.

Whether a translation means what the English means is not mechanical. Translate from the skills' own `SKILL.md` and README rather than word by word, follow `docs/translation-glossary.md`, re-translate only the paragraphs that changed, and then have an independent read-only subagent compare each translation against the English for meaning shifts, glossary violations and the other region's vocabulary. The digest proves only that someone touched the translation after the English changed.

A translation file alone is not a plugin change for the version gate, because nothing reads one at runtime — which is also why `resolve-issue-learnings` excludes `README.*.md` from its oracle glob. Editing an English README inside a plugin still needs the bump, since `resolve-issue/SKILL.md` points its reader at its own README.

A translation shows screenshots of the page in its own language, with the language before the extension, such as `session-dark.zh-TW.jpg`, beside the English ones, and translates a diagram's labels in place. An English page under a Chinese README reads as a page that cannot be had in Chinese, which outweighs what the extra pictures add to each install; English screenshots in the translations were tried first and reversed on 2026-10-09.

The whoami thumbnails live in `docs/whoami/` rather than the plugin folder, the remind-me ones in `docs/remind-me/`, and the dashboard's picture in `docs/issue-to-pr/`, since this README presents several plugin suites where the issue-to-pr README presents one, because the root READMEs are their only readers and every install copies the plugin folder. whoami's and remind-me's are four crops from the plugin's own screenshots of a fictional report, laid out two by two, small enough that the words are not meant to be read, so one light and one dark version serve all three languages; the dashboard is one page, so it is shown whole rather than cut into pieces that lose how they relate. The report is fictional because the README is public and the full-size image can be zoomed until a repository's name reads. Each plugin, or each suite, has a heading, then a line on what it does, then its picture, then a lead-in and its install command; a suite's table goes between its picture and the command. The text names what a plugin does without listing its skills, which the plugin's own README lists. A line under a picture with no heading of its own read as the picture's caption, so the picture-first order of 2026-10-08 was reversed on 2026-10-12.

## Measuring anything (tools we build to check our own work)

**A measurement tool gets checked harder than the thing it measures.** Its output carries the authority of "this was measured", so a wrong number does not just fail — it launders a false conclusion into a decision. Several instruments built here were wrong on their first version and three of those shipped: the dashboard's token count accumulated `usage` **per record with no `message.id` de-duplication**, and read only `input_tokens` / `output_tokens` while ignoring `cache_read_input_tokens` and `cache_creation_input_tokens` entirely — **both halves fixed in `148bd8f`**, which de-duplicates on `(file, message.id)`, reports the cache figures as their own third number, and is pinned by `tests/parse_session_tests.py`'s `test_token_totals` (six mutations, each verified to turn the suite red, the mutation itself verified to be no no-op); the skill-eval runner reported a clean 19/19 + 21/21 split that was `select.select` failing on Windows; and `resolve-issue/SKILL.md` carried a cost anchor that was ~4.3× too high (withdrawn in `fa4aa99` — the line is gone, so do not go looking for it). (That is not a base rate — an instrument that was right first time leaves no debugging trace, so it cannot enter the denominator. It says only that the failure is common enough to need a process rather than care.)

Three rules, in order:

1. **Every check needs a known-answer case that makes it fail — and run it BEFORE the correctness review, not after.** A check that has only ever been run against good input has not been tested. More than that: a review reads a check for whether it is well *built*, and cannot tell you whether it will ever *fire*. Verified here (2026-08-10): a guard survived three `review-plan-risk` passes and two fix rounds, and then its first known-answer case showed it never triggers on the input class it exists for — the premise under it ("a thin ticket yields zero load-bearing claims") was false, because an LLM asked to enumerate claims from vague text invents them instead of returning an empty set. No amount of reading the guard finds that. Fifteen minutes of fixture did. **Treat the fixture as the thing that decides whether to build, not as acceptance work afterwards.** **And a known-answer set proves the check fires on the cases it contains, and nothing else.** A gate built here on 2026-09-21 passed 3/3 planted defects and 4/4 clean controls, then reported 8 hits on the live tree and **all 8 were false** — every planted case was drawn from one direction and the live tree had the other, so the set had never exercised half the input space. Before quoting a pass, name the population the cases came from and add one from the population you have not sampled. Running the control arm *before* the test arm is the cheap version of the same discipline: it tells you what the signal looks like with no effect present, which is prior knowledge rather than acceptance work.
2. **Mutation-test the check set**: delete any one check and the known-answer set must go red. A check that can be deleted without turning the suite red does not exist. This is not hypothetical — an audit tool here passed 4/4 with two of its five checks stubbed out. (A companion example once cited here — "a self-check case had frozen a bug in place" — was withdrawn: on inspection the case was pinning *correct* semantics, and "fixing" it would have weakened the only check that catches a leaked read.)
3. **No result is quotable until 1 and 2 hold.** State the limit instead ("the tool has not been validated"), the same voiced-limit discipline the review skills use.

**Rules 1 and 2 apply to a borrowed instrument too, and the one we borrowed was broken.** `skills-ref` — the Agent Skills spec's own reference validator, from `agentskills/agentskills` — reads `SKILL.md` with `Path.read_text()` and no `encoding=` (`parser.py:89`, `validator.py:172`), so on a cp1252 Windows locale it decodes UTF-8 as one character per **byte** and its 1,024-character description check counts bytes instead. Every em-dash costs 2 phantom characters, an accented letter 1, an emoji 3. Measured with a repro of two descriptions each exactly 1,024 characters long: the all-ASCII one passes, the one made of em-dashes is rejected as **2,992 chars**. Prefix the command with **`PYTHONUTF8=1`** and the same file passes — that is the workaround, and it is also the confirmation of the cause. Three things follow. The failure is one-directional, so it manufactures false failures and never hides a real overage. It is platform-split — the same skill passes on a UTF-8 locale — so a Linux CI run would never surface it and only a Windows contributor sees it. And it was found only because the validator was pointed at a known-bad input first (rule 1) rather than trusted on a clean 14/14: a pass from an instrument that has never been made to fail is not evidence. Current exposure here is nil but thin — the longest real description is `resolve-pr-comments` at 997, which the inflated count puts at 1,005, leaving about nine more em-dashes of room against a house prose style that is full of them.

**A measurement can justify a *concern* without justifying an *instruction* — so mutation-test the instruction, not the observation.** This is the same trap one level up, and it was walked into during the very session that added rules 1 and 2 to a skill. Nine uncontaminated repositories were sampled: 32 of 161 pull request titles began with a bracketed word, and exactly one of those brackets held a ticket reference — the rest were component tags. A true, useful, hard-won number. It was then written into the skill as a rule ("a bracketed word is far more often a component tag than a ticket reference, so do not put a ticket key there"). Removing that clause and re-running the fixture changed nothing, in two cells — including one where the sample was anonymised so no prior knowledge of the project could help. The executor derives it from the sample structurally every time: the tags are words rather than ids, the same tag recurs across pull requests where a per-change key could not, and the tags reappear in bodies as code units. The measurement was real and the instruction was dead weight, competing for attention with the rules that do fire.

So the question a measurement answers is "is there something here to get wrong?", never "does the artifact need a line about it?". Only the second question ships text, and only a fixture answers it. Prefer *enabling* the executor to see the thing — carrying an author field through a format string, say — over *telling* it what to conclude: data cannot misfire, and a rule that duplicates the executor's own reasoning is indistinguishable from one that is simply wrong until you test it.

**Reading Claude Code transcripts — four traps that have already bitten.** Each is verified in this repo, do not re-derive them:

- **`usage` is repeated, tool calls are not.** One API response is written as several `assistant` records — one per content block — and *every* record repeats the same `message.usage`. So summing usage per record multiplies each figure by however many blocks that response held. **That block count differs per response, which is the whole point: there is no inflation ratio to measure once and divide by afterwards** — the repeats have to be dropped as they are read, by de-duplicating on `message.id`. (Do not quote a measured multiple as if it were that ratio. One was recorded here for months and it was a property of one session's content mix, not of the format.) Tool calls need no such care — `tool_use` blocks are written once each, so counts never inherit the inflation, which is why a count is the safer basis for comparison than any token sum. **And "ids are unique" is not an invariant**: across the corpus a number of ids appear more than once, nearly always across different files. **Pair a `tool_use` to its `tool_result` on `(source file, id)`, never on `id` alone** — and key any usage de-duplication on that same pair, for the same reason.
- **A whole session expires together, and a resume reprieves all of it.** Cleanup keys on the **top-level session file's `mtime`**, default **30 days** (`~/.claude/.last-cleanup` records the last run), and it removes the session **together with its `subagents/` directory** — subagent files are not separately retained. Touching a session resets its mtime and spares the entire bundle, so **file age is not evidence of the retention rule**. Evidence (2026-08-07): subagent mtimes cluster at 0–30 days, then a completely empty band from 31 to 43 days, then 14 `agent-*.jsonl` at 44–45 days whose two parent sessions were resumed 3.2 days ago; 0 orphans across 32 subagent directories, in a corpus 129+ days old. **Read that evidence with its limit:** no top-level session older than 30 days survives anywhere, so "zero orphans" is consistent both with "the directory is deleted with its parent" and with "those sessions simply had no subagents". The empty 31–43 band is the load-bearing part; the deletion mechanism itself is inferred, not observed. Plan any transcript-based audit against **30 days from the session's last activity**.

  This one question has now been answered wrongly three times, each way: first a cliff "found" by scanning `find -mtime +28` (a filtered subset cannot establish where a distribution ends — it manufactures the edge it reports); then an over-correction declaring the question unknowable when ten minutes of measurement settles it; then a backwards model built by reading subagent mtimes as exemption instead of as reprieve. **`mtime` is last-append, not creation — it bounds retention but says nothing about content age**, and a resumed session carries months-old records under a recent mtime.
- **A backgrounded subagent's `tool_use` → `tool_result` pair returns in about two seconds, and that is not its runtime.** Measured 2026-09-16 across a consumer repo's 435 `Agent` calls: all 435 pair cleanly, which is exactly what makes the trap quiet — in the newer sessions the pair records *dispatch*, not completion, because the agent runs in the background and reports back later. A duration read off that pair put thirteen writer and verifier agents in one step at 0.0 minutes. The real runtime is the first-to-last timestamp of that agent's own `<session>/subagents/agent-*.jsonl`, and it is the only measure that reads the same way on the older synchronous sessions and the newer background ones.
- **A `<task-notification>` is a plain `user` record, so every "did the session yield to the human" heuristic counts it as a human reply.** It carries string content and no `tool_result`, which is the same shape a typed answer has. This inverted a headline on the first pass: a step whose time was reported as 53 minutes of human waiting against 28 of machine work was really 7 against 77, and the "human" minutes were the orchestrator waiting on its own background agents. Classify a `user` record as human only after excluding `tool_result` blocks **and** the `<task-notification>` / `<system-reminder>` / `<local-command>` text prefixes — and treat any human-versus-machine split that was not built that way as unpublishable rather than approximate, because the error does not shrink the estimate, it reverses it.

Beyond that: `input_tokens` counts only the cache-miss delta once prompt caching is on, so it is not "the input size"; and a per-step window contains whatever the human did during it (one measured step window spent ~47 minutes on an unrelated ticket), so per-step figures are upper bounds on pipeline work, never measurements of it.

## Conventions

Working notes live in `.claude/plans/`, which holds a `.gitignore` of its own that ignores the folder and itself. Nothing there is ever committed, and this repository is public, so that is the place for anything that must not be.

`.gitattributes` pins the working tree to LF on every platform, `*.cmd` excepted.

**This repository is public.** Nothing that reaches the remote may carry internal detail — no organisation's name, no ticket ids in commit subjects, bodies or branch names, and no internal host or repository names. Skill prose uses `acme-…` as the placeholder ticket format. The `leaks` gate catches hosts, GitHub accounts, ticket-shaped tokens and addresses; for anything else, grep a diff before committing.

Commits: a plain summary of 50 characters or fewer, with no prefix and no attribution trailer, committed to `main`.

Prose in skills and docs uses semantic line breaks, except rendered Markdown such as READMEs, which keeps one line per paragraph.
